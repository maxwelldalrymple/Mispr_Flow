# Bug fix: widget froze after releasing fn (PortAudio/CoreAudio deadlock)

- **Branch:** `build` (bug found while on `Rebranding`, same commit `b4d339b`)
- **Machine:** Apple M1 Pro, macOS 26.4, built-in MacBook Pro microphone
- **Raw evidence:** full thread sample of the frozen process: [`*_mic-deadlock-fix.stack-sample.txt`](.)

## Symptom

After ~10 normal dictations, a 15.8 s fn hold never finished: the widget stopped responding. Debug log:

```
[14:29:10.204] fn down (state idle)
[14:29:10.314] state idle -> hold
[14:29:26.031] fn up (held 15.83s)
            <- nothing after this; expected "state hold -> processing"
```

The process was alive but idle (0.4% CPU), so the app was blocked, not crashed.

## Diagnosis

`sample <pid>` of the frozen process (saved next to this log):

**Main thread**, inside `recorder.stop()`, blocked on CoreAudio's HAL I/O mutex:
```
sounddevice stream.stop() -> Pa_StopStream -> FinishStoppingStream (libportaudio)
  -> AudioOutputUnitStop -> AudioDeviceStop -> HALC_ProxyIOContext::StopIOProc
  -> HALB_Mutex::Lock() -> __psynch_mutexwait        (waiting forever)
```

**CoreAudio I/O thread**, inside PortAudio's "is running" property listener, blocked on the audio unit's mutex:
```
HALC_ProxyIOContext::IOWorkLoop -> startStopCallback (libportaudio)
  -> AudioUnitGetProperty -> std::recursive_mutex::lock -> __psynch_mutexwait   (waiting forever)
```

## Root cause

A lock-order deadlock between PortAudio's macOS backend and CoreAudio (bundled PortAudio `V19.7.0-devel`):
the main thread's `AudioOutputUnitStop` holds the audio unit lock and waits for the HAL I/O lock, while the I/O
thread holds the HAL I/O lock and, in PortAudio's `startStopCallback` listener, waits for the audio unit lock.
It is a timing race, not caused by recording length. It could not be caught by unit tests (they use a fake
microphone), and because the main thread is stuck in C code, even the app's SIGTERM cleanup cannot run (the
process had to be force-killed with `kill -9`).

Retrying or restarting the PortAudio stream is not a safe fix: once the HAL I/O context is deadlocked,
further use of the same device in that process can block too.

## Fix plan

1. Replace PortAudio (`sounddevice`) with **AVAudioEngine** (Apple's native audio API, the same one a future
   Swift port would use). It has no PortAudio listener, which was the second party in the deadlock.
2. Resample the mic's native rate (44.1 kHz here) to Whisper's 16 kHz with `soxr` (high-quality streaming resampler).
3. Defence in depth: `stop()` gates capture instantly (no more samples accepted) and stops the engine on a
   background thread, so the UI can never freeze on a stop; if a stop ever hangs, the next recording builds a
   fresh engine instead of reusing the stuck one.
4. Unit tests via an injected engine seam (no real mic), plus an opt-in real-microphone integration test and
   a start/stop soak test.

## Prototype (AVAudioEngine, 40 start/stop cycles, 2 s watchdog on every call)

```
input format: 44100 Hz, 1 ch, interleaved=False
cycles: 40, all started ok: True
start ms: median 131, max 140 | stop ms: median 5, max 13
samples per 0.25 s cycle (expect ~4000): [14035, 2698, 2698, 2698, 2698, 14035] ... peak 1.09
```

- No hangs; stop is ~5 ms.
- ~120 ms of audio at the start of each recording arrives late (PortAudio: ~80 ms): acceptable.
- Missing tail samples in the prototype: the resampler must be flushed on stop (handled in the fix).
- Resampler overshoot can exceed 1.0 slightly (peak 1.09); storage already clips to [-1, 1].

## Implementation

- `whispr/audio.py`: `MicEngine` (thin AVAudioEngine adapter: taps input bus 0 at the native format, delivers channel 0) and a rewritten `Recorder`:
  - capture is gated by a flag under the buffer lock, so no sample is recorded after `stop()` returns;
  - `stop()` flushes the resampler tail, then stops the engine on a `mic-stop` daemon thread (never blocks the UI);
  - `start()` waits up to `STOP_TIMEOUT` (1 s) for the previous stop; if it hung, the engine is abandoned and a fresh one is built;
  - `engine_factory` / `resampler_factory` / `engine_cls` are injected seams for tests.
- `requirements.txt`: `sounddevice` (PortAudio) replaced by `pyobjc-framework-AVFoundation` and `soxr`.

## Verification

**Real-microphone soak** (31 cycles of 0.2-1.2 s plus one 16 s take, 2 s watchdog on every call):

```
prepare: 349 ms, input rate 44100 Hz
cycles: 31, all started: True, all wiped to zero: True
start() ms: median 140, max 157 | stop() ms: median 0.55, max 3.73
audio missing vs wall clock (s): median 0.100, max 0.100
16 s recording: captured 15.90 s, peak 0.101
mic still running after last stop: False
```

- `stop()` now returns in ~0.5 ms (the old PortAudio stop could block forever).
- Start latency ~140 ms, with a consistent ~0.1 s of audio lost at the start of each take (previously ~80 ms).

**Regression test proven.** `test_stop_never_blocks_even_if_coreaudio_hangs` uses an engine whose stop blocks like the deadlock. With the fix reverted to a blocking stop, it hangs and fails (`Timeout (>10.0s)`); with the fix, it passes. `test_hung_stop_switches_to_fresh_engine` covers recovery.

**Tests:** `tests/test_audio.py` rewritten around `FakeEngine` / `IdentityResampler` / `FakeAVAudioEngine` (no real mic); new opt-in `test_real_microphone_start_stop_soak` (21 real cycles, each call watched, captured length checked) passes.

**Mutation testing (audio module):** 110 mutants, 105 killed (95.5%). The 5 survivors are equivalent: `use_errno` (only changes an error message), `rms > 1e-9` variants (far below the -55 dB floor), `>=` on an exact tie, and an `and`->`or` whose second condition cannot differ.

**Suite:** 704 passed, 10 skipped (opt-in integration), green under 5 random orders and 2 parallel runs:


## Known side effect

`soxr` (built with nanobind) prints "leaked function" notices at interpreter exit. These are harmless shutdown notices from the library, not a memory leak in the app.
