# Auto-Enter cues, and a second look at browser text boxes

**Branch:** `speaker-id`

## User reports

1. With Auto-Enter on, dictating into a YouTube comment box copied to the clipboard instead of pasting.
2. Auto-Enter needs a visible or audible cue that it's on.
3. Settings should have a way to turn off sounds.

## Findings

**1. The engine log (15:13) shows the text-box check answered "no" in Chrome three times in a row, then "yes".**
- Auto-Enter was on for all four tries, so it isn't what failed. Auto-Enter acts only after a paste, and the check runs before.
- Every other Chrome dictation in the log was "yes", apart from one "no" at 00:41 with Auto-Enter off.
- A local test page with a focused comment-style box (contenteditable) was detected correctly in the user's Chrome, so the problem couldn't be reproduced.
- Likely cause: focus was still moving into YouTube's comment box, which expands when clicked.

**3. The sound switch already exists:** Settings → System → "Dictation and notification sounds". Nothing was added.

## Changes

- **Browser re-check.** If a browser answers "no text box", the check runs once more 0.15 s later. The log now records the focused element's accessibility roles (e.g. `AXGroup < AXWebArea`), so the next miss shows exactly what Chrome reported.
- **Auto-Enter cues:**
  - a blue ⏎ badge on the widget's corner whenever Auto-Enter is on, idle or recording;
  - turning it on or off plays the lock chime (unless sounds are off) and shows "Auto-Enter on ⏎" or "Auto-Enter off" above the widget.
