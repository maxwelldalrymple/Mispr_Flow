## Failure analysis 1 — leaked file handle (`test_second_instance_exits`)

**Symptom.** Under `-W error`, `tests/test_storage.py::TestSaveRecording::test_recorded_in_keeps_only_app_fields` errors at setup with:

```
ResourceWarning: unclosed file <_io.FileIO name='.../test_second_instance_exits0/Mhispr_Flow.lock' mode='wb'>
pytest.PytestUnraisableExceptionWarning: Exception ignored in: <_io.FileIO ... Mhispr_Flow.lock>
```

The failing test passes in isolation, so the warning was produced elsewhere and surfaced when the garbage collector ran.

**Root cause.** `app._single_instance_lock()` opens the lock file, and when `flock` fails it calls `sys.exit(1)` without closing the file. `test_second_instance_exits` exercises exactly that path, so every run leaked one file object; whichever test was running when it was collected got blamed. This is a real (minor) defect in the app, not only in the test.

**Test design problems.**
1. The test redirected the lock location by monkeypatching `tempfile.gettempdir` (patching a global dependency instead of injecting one).
2. No test asserted that the failure path releases resources, so the leak was invisible.
3. Warnings were not errors in the normal suite, so the problem only showed under stress.

**Fix.**
- App: `_single_instance_lock(path=LOCK_PATH)` takes the path as a parameter (dependency injection) and closes the file before exiting.
- Tests: rewritten around an injected `lock_path` fixture and a context-managed "other instance" holder; new test asserts the failure path emits no `ResourceWarning` (forced `gc.collect()` under `warnings.catch_warnings`).
- Suite: `filterwarnings = ["error"]` in `pyproject.toml`, so any warning now fails the normal run, not just the stress run.

**Verification.** With the fix reverted (`lock.close()` replaced by `pass`), `test_second_instance_releases_its_file` fails; with the fix it passes. Full suite: 513 passed, 7 skipped, with `filterwarnings = error`.

## Failure analysis 3 — order-dependent test (`test_content_fades_in`, 1/15 random seeds)

**Symptom.** Failed only with `--randomly-seed=10`.

**Root cause.** The fake pointer (`Pointer.location`) was a class attribute, so the position a previous test left behind leaked into the next one. When it happened to be outside the widget, the first `tick()` closed the HOVER state and reset the fade, so `content_a` was not the expected value.

**Fix.** `make_pointer()` builds a fresh pointer per test, parked off-widget until the test places it (no shared mutable state). The test now uses HANDSFREE, a state the pointer cannot change, so it tests only the fade. Verified: seed 10 plus 30 further random orders (seeds 200-229) all pass.
